# Bug 修复执行规范

## 核心原则

1. **先定位，再修复** — 禁止跳过分析直接改代码
2. **数据优先于代码** — 先验证数据，再看逻辑
3. **最小修改原则** — 仅改必要部分，不重写无关代码
4. **必须验证结果** — 未验证不得声称"已修复"

## 9 步流程（严格顺序执行）

### Step 1: 问题定义（禁止跳过）

```
输入：[触发 bug 的操作/数据]
预期：[应该发生什么]
实际：[实际发生了什么]
问题：[偏差总结]
```

### Step 2: 原因分析（至少 3 个假设）

列出可能原因，覆盖：逻辑错误、边界条件、状态/变量错误、数据异常、调用/接口错误、时序/异步问题。

### Step 3: 定位过程（必须模拟执行）

- 使用具体输入，逐步执行逻辑
- 展示关键变量变化
- 指出异常出现的精确位置
- **禁止**只阅读代码就下结论

### Step 4: 数据验证

- 空值 / NaN / 未初始化？
- 数据结构完整？字段缺失？
- 边界：空输入、极端值、临界条件

### Step 5: 风险点检查（至少 3 个）

主动检查：下标越界/off-by-one、条件判断错误、状态未更新、类型错误、精度问题、重复/遗漏执行。

### Step 6: 根因确认（禁止猜测）

```
错误位置：[file:line]
错误类型：[分类]
发生原因：[具体原因]
```

无法确定时必须说明"不确定"并指出缺失信息。

### Step 7: 修复方案设计

说明修改思路、范围、是否影响其他逻辑、是否有副作用。**先说方案，再写代码。**

### Step 8: 代码修改

- 仅修改必要部分
- 标注修改位置
- 不得重写无关代码

### Step 9: 验证修复

- 正常测试：原始问题是否解决
- 边界测试：极端情况是否正常
- 反例测试：尝试再次触发 bug

## 禁止行为

- 跳过分析直接改代码
- 未模拟执行就下结论
- 未验证就说"已修复"
- 大范围重写代码
- 编造不存在的逻辑或接口
